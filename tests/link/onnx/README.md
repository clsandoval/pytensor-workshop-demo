# ONNX Backend Testing

This directory contains tests for PyTensor's ONNX export functionality, using a hybrid approach combining **property-based testing** with **targeted regression tests**.

## Test Organization

### Property-Based Tests (`test_properties.py`)

Comprehensive tests using Hypothesis that verify fundamental properties for all operations:

- **test_onnx_matches_pytensor**: Core correctness - ONNX must match PyTensor output
- **test_elemwise_preserves_broadcast_shape**: Shape broadcasting works correctly
- **test_operation_preserves_dtype**: Dtype handling is correct
- **test_operation_handles_edge_cases**: No crashes on edge cases

**Why property-based testing?**
- Automatically discovers edge cases (empty tensors, extreme values, unusual shapes)
- Tests 10-1000 random inputs per property (configurable)
- Shrinks failures to minimal examples
- Reduces test code from 100+ manual tests to ~4 generic properties

**Running property tests:**
```bash
# Fast (10 examples per property) - for development
uv run pytest tests/link/onnx/test_properties.py --hypothesis-profile=dev -v

# Thorough (100 examples per property) - for CI
uv run pytest tests/link/onnx/test_properties.py --hypothesis-profile=ci -v

# Exhaustive (1000 examples per property) - for release validation
uv run pytest tests/link/onnx/test_properties.py --hypothesis-profile=thorough -v
```

### Regression Tests (`test_regressions.py`)

Specific tests for bugs that were fixed. Each test documents:
- What broke
- How it was fixed
- Where the fix is in the codebase

**Categories:**
- **DimShuffle regressions**: Identity node misuse, squeeze+transpose patterns
- **Composite operations**: Cast in Composite, Sqr scalar op
- **Structure validation**: Cast node attributes, DeepCopyOp → Identity
- **Conv2D critical tests**: Filter flipping (MOST IMPORTANT), asymmetric padding, grouped convolution, dilation

These serve as fast smoke tests (~9 seconds) and documentation.

### Basic Tests (`test_basic.py`)

Core infrastructure tests:
- ONNX export functionality
- Helper functions (`compare_onnx_and_py`, `validate_onnx_graph_structure`)
- Shared variables as initializers
- DeepCopy operation

### Operation-Specific Tests

Manual tests for specific operations that need detailed validation:

- **test_elemwise.py**: Elemwise operations (add, mul, sub, div, exp, log, sqrt, etc.)
- **test_shape.py**: Shape operations (reshape, dimshuffle, transpose, squeeze, unsqueeze, AllocEmpty)
- **test_nlinalg.py**: Linear algebra (dot, matrix multiplication, Gemv)
- **test_special.py**: Special functions (Softmax, ReLU/Maximum, Minimum)
- **test_conv.py**: Convolution operations (Conv2D with all configurations)

**Note:** Many of these tests are now covered by property tests, but are kept for:
1. Specific edge cases not easily generated by Hypothesis
2. Integration tests (e.g., Conv → ReLU → Flatten)
3. Detailed documentation of operation behavior

## Test Infrastructure

### Hypothesis Strategies (`strategies/`)

Reusable input generation for property tests:

**Core strategies** (`strategies/core.py`):
- `onnx_dtypes()`: ONNX-supported dtypes (float32, float64, int32, int64)
- `valid_shapes()`: Valid tensor shapes with configurable rank and dimensions
- `onnx_tensor()`: Generate ONNX-compatible tensors with safe numeric ranges

**Operation strategies** (`strategies/operations.py`):
- `unary_operation_inputs()`: For operations like neg, exp, log
- `binary_broadcastable_inputs()`: For operations like add, mul with broadcasting
- `matmul_inputs()`: For matrix multiplication with compatible shapes
- `reshape_inputs()`: For reshape with compatible target shapes
- `conv2d_inputs()`: For 2D convolution with various configurations

**Operation Registry** (`ONNX_OPERATIONS`):
Central registry mapping operation names to test configurations:
```python
ONNX_OPERATIONS = {
    "add": OperationConfig(
        op_func=lambda x, y: x + y,
        input_strategy=binary_broadcastable_inputs(),
        valid_dtypes=["float32", "float64", "int32", "int64"],
        category="elemwise",
    ),
    # ... 10 more operations
}
```

### Hypothesis Configuration (`conftest.py`)

Profiles configured for different environments:

| Profile | Examples | Deadline | Use Case |
|---------|----------|----------|----------|
| **dev** (default) | 10 | 500ms | Fast feedback during development |
| **ci** | 100 | None | CI/CD pipelines |
| **thorough** | 1000 | None | Release validation |
| **onnx** | 50 | 5s | ONNX-specific tests (slow operations) |

Set profile via environment variable:
```bash
HYPOTHESIS_PROFILE=ci uv run pytest tests/link/onnx/test_properties.py
```

## Adding Tests for New Operations

**DO NOT write manual tests for routine operations.** Instead:

### 1. Add operation to the registry

Edit `strategies/operations.py`:

```python
ONNX_OPERATIONS["new_op"] = OperationConfig(
    op_func=pt.new_op,
    input_strategy=appropriate_strategy(),  # Use existing or create new
    valid_dtypes=["float32", "float64"],
    category="elemwise",  # or "shape", "nlinalg", etc.
    notes="Optional notes about constraints"
)
```

### 2. Create custom input strategy (if needed)

If the operation needs special input generation:

```python
@st.composite
def new_op_inputs(draw):
    """Generate valid inputs for new_op.

    Returns
    -------
    tuple
        (input1, input2, ...) - Inputs with appropriate constraints
    """
    dtype = draw(st.sampled_from([np.float32, np.float64]))
    shape = draw(valid_shapes())
    x = draw(onnx_tensor(dtype=dtype, shape=shape))
    # Add any special constraints or filtering here
    return (x,)
```

### 3. Property tests automatically test your operation

Run the property tests - they will automatically include your new operation:

```bash
uv run pytest tests/link/onnx/test_properties.py::test_onnx_matches_pytensor --hypothesis-profile=dev -v
```

### 4. Add regression test only if you discover a specific bug

If you find a specific bug or edge case that's hard to reproduce:

```python
def test_new_op_specific_bug_regression(tmp_path):
    """
    Regression: New_op fails with specific edge case.

    Bug: [Description of what went wrong]
    Fixed: [How it was fixed]
    Reference: [Location in codebase]
    """
    # Minimal reproduction of the bug
    x = pt.vector("x", dtype="float32")
    y = pt.new_op(x)

    x_val = np.array([...], dtype="float32")  # Specific values that triggered bug

    compare_onnx_and_py([x], y, [x_val], tmp_path=tmp_path)
```

## Helper Functions

### `compare_onnx_and_py(graph_inputs, graph_outputs, test_inputs, *, tmp_path)`

Main helper that:
1. Compiles PyTensor function
2. Exports to ONNX
3. Runs with ONNX Runtime
4. Compares outputs with `np.testing.assert_allclose`

**Parameters:**
- `graph_inputs`: List of symbolic PyTensor variables
- `graph_outputs`: Symbolic output variable(s)
- `test_inputs`: Concrete numpy arrays for testing
- `tmp_path`: Temporary directory (pytest fixture)

**Returns:** `(session, onnx_results)`

### `validate_onnx_graph_structure(model, *, expected_node_types, expected_node_count)`

Validates ONNX graph structure beyond numerical correctness:
- Checks node types match expected
- Verifies node count
- Validates all connections are valid

Useful for regression tests that verify specific ONNX structure.

## Debugging Hypothesis Failures

When Hypothesis finds a failure:

1. **Let shrinking complete** - Hypothesis will reduce the failing case to a minimal example
2. **The failure is saved** in `.hypothesis/examples/`
3. **Add to regression tests**:
   ```python
   @given(...)
   @example(failing_case_from_hypothesis)  # Lock in the failure
   def test_operation(...):
       ...
   ```
4. **Fix the bug**
5. **Verify the `@example()` now passes**
6. **Keep the test** as regression prevention

### Common Hypothesis Issues

**"Too many filtered examples"**: Your `assume()` conditions are too restrictive
- Solution: Generate valid data directly instead of filtering

**"Flaky test"**: Test passes sometimes but fails others (timing issues)
- Solution: Use `deadline=None` for slow ONNX operations

**"Health check failed"**: Using pytest fixtures with `@given`
- Solution: Add `@settings(suppress_health_check=[HealthCheck.function_scoped_fixture])`

## Test Statistics

**Before property-based testing:** 103+ manual tests (growing linearly with each operation)

**After implementation:**
- **Property tests:** 4 generic tests (test ALL operations)
- **Regression tests:** 11 specific bug tests
- **Operation tests:** ~80 tests for specific behaviors and integration
- **Total:** ~95 tests (vs 103+), but with **much better coverage**

**Key improvements:**
- Adding new operation: 1 registry entry instead of 5-10 manual tests
- Automatic edge case discovery (empty tensors, extreme values, unusual shapes)
- Configurable thoroughness (10 to 1000 examples per property)

## Known Limitations

### Operations Not Yet Supported
- Matrix decompositions (SVD, QR, Cholesky)
- Advanced pooling operations
- Recurrent operations (RNN, LSTM, GRU)
- Some shape operations (MakeVector, Scan)

### ONNX Runtime Limitations
- FusedMatMul only supports float32 (not float64)
- Some operations have restricted dtype support
- CPU vs GPU execution providers may have different capabilities
